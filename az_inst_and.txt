Below is the overall design, followed by the questions that will finalize it. The draft YAML in azure-pipelines-ahs-android.yml follows this design. Its placeholders are marked TODO so Copilot can fill them in.

The flow
Someone runs the pipeline manually and picks the Environment (Dev/QA/UAT/Prod), the Play track, and whether the upload is a draft.
Build stage: The agent installs .NET 10, JDK 17, and the maui-android workload. It downloads your keystore and runs dotnet publish on only AHS.Maui.csproj, using -c Publish_<env> and -f net10.0-android. That build produces an AAB signed with your upload key, which is saved as a pipeline artifact.
Upload stage: This is a deployment job tied to an Azure DevOps Environment, so Prod can require an approval. It uploads the AAB to Play through the Google Play extension.
What you need to create (one-time setup)

In Google Cloud and Play Console

A Google Cloud project with the Google Play Android Developer API enabled.
A service account in that project, plus a JSON key for it.
In Play Console, go to Users and permissions and invite the service account’s email. Grant it release permissions for this app only.
Your organization is government. Check early whether creating service account keys is allowed by policy. That is the most likely blocker.

In Azure DevOps

Install the Google Play extension from the Marketplace. It provides the GooglePlayRelease task.
Create a service connection of type Google Play, using the JSON key.
Upload the keystore under Pipelines > Library > Secure files.
Create a variable group containing the key alias, the store password (secret), and the key password (secret).
Create Environments named AHS-Play-Dev, QA, UAT, and Prod. Put an Approvals check on Prod, and optionally a branch restriction (main only).
Lock the secure file, variable group, and service connection to this one pipeline instead of “all pipelines”. Then control who can run it through pipeline permissions.
Signing (avoiding the two-day wait)

The “Ad hoc” choice in Visual Studio is only a distribution label. What matters is the keystore. You almost certainly use Play App Signing, which means your local keystore holds the upload key. As long as the pipeline signs with that same keystore and alias, Play accepts the bundle immediately. The wait only happens if the upload key changes.

To confirm you have the right key:

Run keytool -list -v -keystore yourfile.keystore -alias youralias and note the SHA-1.
In Play Console, open App integrity > App signing and compare it to the upload key certificate SHA-1. They should match.

The pipeline passes the passwords using MSBuild’s env: prefix, so they never appear on the command line. Keep an offline backup of the keystore. Secure Files cannot be downloaded back out of DevOps.

Versioning

Play requires each upload’s version code to be unique and higher than every previous upload for that package. This is true across all tracks, not per track.

I recommend splitting the two version numbers:

Version code (ApplicationVersion): set automatically by the pipeline with a DevOps counter(). Seed it above your current highest code.
Display version (ApplicationDisplayVersion): keep bumping this manually in the csproj, as you do today.

This prevents failed uploads from someone forgetting to increment. It also avoids having the pipeline commit version changes back to the repo, which gets messy.

Configuration gotcha

When you publish AHS.Maui with -c Publish_QA, that configuration name flows into the four referenced projects as well. If those projects don’t define Publish_*, they build with no Optimize/Release defaults.

Check that every project treats Publish_* like Release. A Directory.Build.props at the solution root with a condition such as $(Configuration.StartsWith('Publish_')) that sets Optimize=true is the cleanest way to do that.

Those answers settle the design. Here is what each one changed in azure-pipelines-ahs-android.yml.

1. One Play app

The pipeline now uses one package name, which you fill in from your csproj. It already had one version code counter shared by all four branches, and that is now required. All four environments go into the same Play app, so a QA build and a Prod build can never have the same version code. Seed the counter above the highest version code you have uploaded so far.

This creates one new problem. Every bundle in the library will look alike, so you need to tell a QA bundle from a Prod bundle there. To fix that, the pipeline reads ApplicationDisplayVersion from the csproj and adds a tag to it for every environment except Prod. A QA build shows up as 2.4.1-qa (1043), and a Prod build shows up as plain 2.4.1 (1044). The pipeline run in DevOps is renamed the same way, so the run history matches what you see in Play. This keeps someone from accidentally pushing a Dev-configured bundle to production later.

2. Getting the bundle into the library

The “Library” option in that dialog lists what’s in App bundle explorer. The Google Play upload task can’t drop a bundle into the library by itself, because it always attaches the bundle to a track. The draft defaults (internal track, draft release) get you the same result:

The bundle lands in App bundle explorer, ready to select when you create a release.
Nothing rolls out to anyone.
Each run’s draft replaces the previous draft on the internal track. The earlier bundles stay in the library, so nothing is lost.

When you’re ready for the closed-testing phase, you change two parameters: track alpha (Play’s API name for the default closed track) and draft off. No restructuring is needed.
